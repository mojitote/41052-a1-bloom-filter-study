## 0:00–0:35 项目和结果

打开 README 和 `include/bloom.hpp`：这是 Track A，研究 Bloom filter 的误报率、容量、内存和查询性能。强调 `contains` 的 true 是“可能存在”；false 是“一定不存在”，前提是正确实现、无删除和状态没有损坏。

## 0:35–1:25 核心实现

展示构造函数、`position`、`insert`、`contains`。m 是位数，k 是哈希次数，seed 决定可重复的映射。每个 64-bit word 保存 64 个标记。`p / 64` 找到字，`p % 64` 找到字里的位置。哈希使用非密码学 mixer，不声称不同盐就证明了独立性。

## 1:25–2:10 一个不变量

展示 `words_[p / 64] |= UINT64_C(1) << (p % 64)`。

“插入只把位变成 1，不会把已经是 1 的位改回 0。查询使用相同参数和位置，因此每个插入过的元素所需的位都还在。这就是不漏报的原因。”

解释这个保证不依赖随机性：即使哈希很差，误报会变多，但正确插入过的键仍不应该漏报。

## 2:10–2:50 难点和 what breaks

运行：

```sh
make demo
```

展示 key 10 的位置 30、14、16，key 37 的合法误报，再打开 `src/demo.cpp` 中的独立 mutation。把 `|=` 改成 `=` 会覆盖同一个 word 的其他位，导致 key 10 从存在变成不存在。说明这段代码是刻意构造的教学反例。

也可以指出 `UINT64_C(1)` 的目的：防止用窄的有符号整数构造高位掩码。

## 2:50–4:00 实验和学习

打开 `figures/speedup.png` 和 `figures/early_exit.png`：

- 10 bits/key、7 hashes 的误报率约 0.821%，符合近似公式。
- 更低误报率不等于更快的完整系统；只用 1 hash 的 exact pipeline 在全部查询不存在时约 2.71× 加速。
- 早退版本平均检查约 2 个位，仍可能慢于检查全部 7 个位。实验展示了差异，但没有硬件计数器，所以不能宣称已证明是分支预测造成的。
